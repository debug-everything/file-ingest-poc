# AGENTS.md — Streaming Pass-Through POC (1 GB file via facade)

> Instructions for a coding agent. Read this whole file before writing code.
> Build in the phase order at the bottom. Do not skip the acceptance checks.
> **Update (Oct 2026):** the facade is hosted on **Railway**, not Render. Wherever this file says Render,
> read Railway. The README has the current deploy steps, costs and limits.

## 1. Purpose

Prove (or disprove) that a **stateless pass-through facade** can stream a ~1 GB file from a partner
File API to an MFT client **without buffering**, with flat memory, correct backpressure, and clean
abort handling, across three separate networks. It simulates this production path:

```
MFT app (scheduled pull, writes file)  ──GET──▶  Facade API (stateless, streams)  ──GET──▶  Partner File API (source of 1 GB file)
       [network C]                                    [network B]                              [network A]
```

The real-world analogue is a Stripe settlement/fee file pull: the MFT tool can only call a
**static, pre-configured URL**, so the facade resolves "the latest file of type X" to a dynamic
file ID and streams `GET /v1/files/:id/contents` back to the MFT tool. No persistence, no object
storage, no disk spooling in the facade.

### Questions this POC must answer
1. Does facade memory stay flat (bounded by stream buffers) for a 1 GB transfer?
2. Does backpressure propagate end-to-end (slow MFT → facade slows its upstream read)?
3. What CPU does the facade spend per GB on a small (≈0.1 vCPU / 512 MB) container?
4. Does any platform ingress/proxy buffer the response (visible as late TTFB at the client)?
5. When the client aborts, does the facade tear down the upstream request promptly?
6. Can a `Range` request resume a partial download through the facade?
7. End-to-end duration from "MFT triggers call" to "file fully written and fsync'd".

## 2. Components

| Component | Language | Role | Hosted on |
|---|---|---|---|
| `partner-file-api` | Node.js 22 (ESM, no framework) | Serves pre-generated CSV test files (10 MB, 100 MB, 500 MB, 1 GB) from disk with Stripe-like endpoints, Range support, checksum. **Local only.** | Local (docker-compose) |
| Partner in the cloud | Static: GitHub Release assets + `manifest.json` | Same files and checksums, served by GitHub's download CDN (see §8) | Network A: GitHub release CDN |
| `facade-api` | Node.js 22 (ESM, `node:http` + `undici`) | Resolves latest file ID, streams bytes through, logs CPU/mem at start/during/end | Network B: Render |
| `mft-client` | Python 3.12 (`httpx`, async) + a `curl` mode | Triggers the pull, writes to disk, verifies checksum, logs total duration, merges facade metrics into a report | Network C: GitHub Actions runner (Azure) |

**Hard constraint: every hosted piece must be usable without a credit card.**

Why no framework in the facade: Express/Nest/Fastify add layers that can hide buffering. Use raw
`node:http` so every byte path is explicit. (A NestJS variant can be a follow-up to check whether
the framework changes the memory profile.)

## 4. Partner File API (network A)

The partner exists in two forms that serve **byte-identical files**:
- **Local:** the `partner-file-api` Node service below. It has request logs, Range, auth, a
  concurrency guard and `throttle_kbps`, so it is what the local scenarios (S2–S6) are judged on.
- **Cloud:** a static partner on GitHub Releases (§8). No compute, no card, no bandwidth cap. The
  facade talks to it through the same two-step "resolve latest, then fetch contents" flow.

### Endpoints
| Method | Path | Behavior |
|---|---|---|
| GET | `/healthz` | `200 {"ok":true}` — no auth |
| GET | `/v1/files?purpose=settlement&variant=100mb&latest=true` | `200 {"id":"file_settle_100mb","variant":"100mb","size":104857600,"sha256":"...","created":...}`. `variant` defaults to `DEFAULT_VARIANT` (env, default `100mb`). Unknown variant → `404`. |
| GET | `/v1/files/:id` | File metadata (same shape) |
| GET | `/v1/files/:id/contents` | Streams the pre-generated file from disk. Supports `Range: bytes=start-end` → `206` + `Content-Range`. Sets `Content-Length`, `Content-Type: text/csv; charset=utf-8`, `ETag` (= sha256), `Accept-Ranges: bytes`, `Content-Encoding` absent. Never compresses, even if the client asks for gzip. |

### Pre-generated test files
Four files are generated **once at deploy time**, never at request time, so the GET endpoint only
does disk reads (no CPU spent producing data, no generation latency in the measurements):

| Variant | File ID | Size (exact) | Used for |
|---|---|---|---|
| `10mb` | `file_settle_10mb` | 10,485,760 B | Smoke tests, wiring, auth, error codes |
| `100mb` | `file_settle_100mb` | 104,857,600 B | Iteration runs until everything works; S2–S6 |
| `500mb` | `file_settle_500mb` | 524,288,000 B | Abort/resume (S5), optional mid-size data point |
| `1gb` | `file_settle_1gb` | 1,073,741,824 B | The 2–3 final recorded runs |

Total ≈ 1.6 GiB on disk.

### Rules
- **Auth:** `Authorization: Bearer $PARTNER_TOKEN` on everything except `/healthz`. These endpoints are
  public on the internet; an unauthenticated 1 GB endpoint will burn egress quota from scanners.
- **Concurrency guard:** at most `MAX_CONCURRENT_DOWNLOADS` (default 2) active streams; extra → `429`.
- **File generation** (`src/generate.js`, `npm run generate`): writes `DATA_DIR/<id>.csv` plus
  `<id>.sha256` and `<id>.json` (metadata) for each variant in `VARIANTS` (default
  `10mb,100mb,500mb,1gb`).
  - Content is settlement-like CSV text: a header row
    (`txn_id,created,merchant_id,amount,currency,fee,net,type,description`) followed by rows with
    randomized values, so it resembles a real settlement file.
  - Stream rows into a write stream in ~1 MiB batches, respecting backpressure. Pad or truncate the
    final row so the file is **exactly** the target byte size (stable sizes make throughput
    comparisons clean). Compute sha256 incrementally while writing.
  - **Idempotent:** if `<id>.csv` exists, its size matches, and its sha256 matches the sidecar, skip
    it. `--force` regenerates. Generation is a one-time step (`npm run generate` locally; the
    `publish-test-files.yml` workflow for the cloud); the local server refuses to start if any
    configured variant is missing.
  - Use a seeded PRNG (`SEED` env) so local and cloud files are byte-identical and the expected
    sha256 values can be checked into `partner-file-api/checksums.json`.
  - Never commit the generated files; add `DATA_DIR` to `.gitignore`.
- **Text is compressible, so guard against silent compression.** Gzip by any hop would shrink the
  bytes on the wire and make throughput meaningless. Partner never sets `Content-Encoding`. The facade
  sends `Accept-Encoding: identity` upstream. The MFT sends `Accept-Encoding: identity` and reads raw
  bytes (`aiter_raw`, not `aiter_bytes`). The MFT fails the run if bytes written ≠ `Content-Length`
  or if any response carries `Content-Encoding`.
- **Partner metadata is cached in memory at startup** from the `.json` sidecars. Requests never
  hash or stat large files.
- Serve with `fs.createReadStream(path, { start, end, highWaterMark: 64 * 1024 })` + `stream.pipeline`.
- Optional `?throttle_kbps=N` query to simulate a slow partner.
- Log one JSON line per request: `{ts, reqId, path, range, status, bytesSent, durationMs, aborted}`.

## 5. Facade API (network B) — the system under test

### Endpoints
| Method | Path | Behavior |
|---|---|---|
| GET | `/healthz` | `200` — no auth; used for warm-up |
| GET | `/files/:purpose` | Static URL the MFT calls (e.g. `/files/settlement`). Resolves latest ID from partner, then streams contents. Forwards client `Range` header. Optional `?variant=10mb|100mb|500mb|1gb` is passed through to the partner lookup (test-only knob; in production the URL stays fully static). |
| GET | `/runs/:runId/metrics` | Returns the collected metric samples for a run (JSON array). Auth required. |
| GET | `/runs` | Last 20 run summaries. |

Query flags on `/files/:purpose` (for experiments only):
- `mode=stream` (default) | `mode=buffer` — buffer mode deliberately reads the whole upstream body
  into memory before responding. It exists to show the failure mode. Refuse `mode=buffer` if the
  upstream `Content-Length` exceeds `BUFFER_MODE_MAX_BYTES` (default 150 MiB) so the demo doesn't
  just crash the free instance; return `413`. In practice: `100mb` works and shows the growth;
  `500mb` and `1gb` are refused.
- `hwm=<bytes>` — override `highWaterMark` for the response pipe (default 64 KiB).

### Partner modes (`PARTNER_MODE` env)
Both modes keep the same two-step shape as Stripe: resolve the latest file, then stream its contents.
- `api` (local default): `GET $PARTNER_BASE_URL/v1/files?purpose=…&variant=…&latest=true` with
  `Authorization: Bearer $PARTNER_TOKEN`, then `GET /v1/files/:id/contents`.
- `static` (cloud default): fetch `$PARTNER_MANIFEST_URL` (the release's `manifest.json`), cache it
  in memory for `MANIFEST_TTL_MS` (default 5 min), pick the entry for the variant, then
  `GET entry.url`. GitHub answers the asset URL with a `302` to a signed CDN URL, so the upstream
  call **must follow redirects** (`undici` `maxRedirections: 3`, or an interceptor) and must re-send
  `Range` on the redirected request. Record the redirect hop's latency separately in the `start` →
  `first_byte` gap (add `redirectMs` to the `first_byte` sample). No partner token in this mode.

### Streaming implementation requirements
- Use `undici.request()` (or global `fetch` + `Readable.fromWeb`) for the upstream call; pass an
  `AbortController` signal.
- `await stream.promises.pipeline(upstreamBody, meterTransform, res)`. Never call `.text()`,
  `.arrayBuffer()`, `.json()` on the file body in stream mode.
- `meterTransform` is a pass-through `Transform` that counts bytes and records when `res.write`
  returned `false` (backpressure events). It must not copy or retain chunks.
- If `res` emits `close` before `finish` (client aborted), abort the upstream controller and record
  `phase:"aborted"`.
- Propagate response headers: `Content-Length`, `Content-Type`, `Content-Range`, `Accept-Ranges`,
  `ETag`. Add `X-Run-Id`, `X-Upstream-File-Id`, `Cache-Control: no-store`. Strip hop-by-hop headers.
  Do not set `Content-Encoding`.
- **Status mapping:** no file found for purpose → `404`; partner 4xx/5xx or connect failure before
  first byte → `502` (with `X-Upstream-Status`); facade bug → `500`. Once headers are sent, errors
  can only be signaled by destroying the socket — log it.
- **Correlation:** accept `X-Run-Id` from the client (generate a ULID if absent); forward it to the
  partner as `X-Request-Id`; include it in every log line.
- **Auth:** require `Authorization: Bearer $FACADE_TOKEN` from the MFT (the Render URL is public;
  an open 1 GB endpoint would burn the 5 GB cap). Use `$PARTNER_TOKEN` upstream in `api` mode only.

### Metrics sampler (`src/metrics.js`) — the core requirement
Emit JSON-lines to stdout **and** keep them in the run's ring buffer. Phases:
- `start` — immediately before the upstream request is issued
- `first_byte` — when the first upstream chunk arrives
- `sample` — every `METRICS_INTERVAL_MS` (default 1000) **and** every 64 MiB transferred
- `end` | `aborted` | `error` — when the pipeline settles

Each sample:
```json
{
  "ts": "2026-09-30T20:41:07.123Z",
  "runId": "01J...",
  "phase": "sample",
  "elapsedMs": 4210,
  "bytes": 268435456,
  "throughputMBps": 61.2,
  "backpressureEvents": 1834,
  "cpu": { "userMs": 812.4, "systemMs": 401.1, "pctOfOneCoreSinceLast": 9.6 },
  "mem": { "rss": 71303168, "heapUsed": 9123456, "heapTotal": 16777216, "external": 2101248, "arrayBuffers": 1310720 },
  "cgroup": { "memCurrent": 88080384, "memMax": 536870912, "cpuNrThrottled": 412, "cpuThrottledUsec": 3120000 },
  "eventLoop": { "p50Ms": 10.1, "p99Ms": 24.3, "maxMs": 40.2 }
}
```
- CPU: `process.cpuUsage(prev)` deltas divided by `process.hrtime.bigint()` deltas.
- Memory: `process.memoryUsage()`.
- cgroup v2: read `/sys/fs/cgroup/memory.current`, `/sys/fs/cgroup/memory.max`,
  `/sys/fs/cgroup/cpu.stat` (`nr_throttled`, `throttled_usec`). Fall back to cgroup v1 paths; if
  neither exists, emit `null` — never crash. **cgroup numbers matter**: on a 0.1 vCPU instance,
  CPU throttling, not the network, may cap throughput, and that must be visible.
- Event loop: `perf_hooks.monitorEventLoopDelay({ resolution: 10 })`, reset per sample.
- Use `setInterval(...).unref()`. Note: if the event loop is starved, samples will arrive late —
  record actual `elapsedMs`, never the intended interval.
- `end` sample also includes a summary: `{ totalBytes, durationMs, avgMBps, peakRss, peakHeapUsed,
  rssDeltaFromStart, cpuMsPerGB }`.

## 6. MFT client (network C)

### CLI
```
python -m mft run \
  --facade-url https://<facade-host>/files/settlement \
  --token $FACADE_TOKEN \
  --variant 100mb \
  --out /tmp/settlement.csv \
  --expected-sha256-from checksums   # checksums.json in repo (default) | manifest | literal hex
  [--mode httpx|curl] [--read-rate-mbps 5] [--abort-after-mb 200] [--resume] [--warmup]
```
`--variant` defaults to `100mb`. Going to `1gb` should be a deliberate choice, never a default.

### Behavior
- `--warmup`: call facade `/healthz` (and partner `/healthz` in `api` mode) first, record
  cold-start time separately; the measured run starts only after they return 200. On Render the
  facade wake can take ~1 min — that must never land inside the measured duration.
- Generate `runId` (ULID), send as `X-Run-Id`.
- **Timer starts** immediately before the request is sent (`t0 = time.perf_counter_ns()`).
- Record `ttfb` (response headers received) and `firstByte` (first body chunk).
- Stream with `httpx.AsyncClient(timeout=httpx.Timeout(connect=10, read=60, write=60, pool=10))`,
  `async for chunk in resp.aiter_raw(65536)` → write to file; hash with `hashlib.sha256` incrementally.
- `--read-rate-mbps`: sleep between chunks to throttle consumption (backpressure scenario).
- `--abort-after-mb`: close the response early (abort scenario).
- `--resume`: if `--out` exists partially, send `Range: bytes=<size>-`, append, then hash the full
  file at the end.
- **Timer stops** after `f.flush()`, `os.fsync(f.fileno())`, `f.close()`. That is the
  "file completely written" moment.
- Then `GET /runs/:runId/metrics` from the facade and merge.
- `--mode curl`: run `curl_mode.sh`, which uses
  `curl -sS -o $OUT -H ... -w '%{json}'` and parses `time_namelookup, time_connect,
  time_appconnect, time_starttransfer, time_total, size_download, speed_download`. This mirrors
  how the real MFT tool pulls via a cURL script.

### Output
`results/<runId>.json`:

## 7. Test scenarios

All scenarios run locally (docker-compose) as many times as needed. Only a handful run in the
cloud; see the run plan below. Single runs are fine; no repeats/medians required.

| ID | Scenario | Variant | How | Pass criteria |
|---|---|---|---|---|
| S0 | Smoke | `10mb` | default | 200, checksum ok, all metric phases present, auth/404/502 codes correct |
| S1 | Baseline stream | `100mb` → `1gb` | default | checksum ok; facade `rssDeltaFromStart` peak < 64 MiB |
| S2 | Slow consumer | `100mb` | `--read-rate-mbps 5` | facade RSS flat; `backpressureEvents` high; partner request duration ≈ client duration (backpressure reached upstream) |
| S3 | Buffer anti-pattern | `100mb` | `mode=buffer` | RSS grows ≈ 100 MiB; `500mb` request returns `413` |
| S4 | Client abort | `100mb` | `--abort-after-mb 40` | facade logs `aborted` within 2 s; partner log shows `aborted:true` |
| S5 | Resume via Range | `500mb` | `--abort-after-mb 200`, then rerun with `--resume` | final checksum ok; partner logged a `206` |
| S6 | Concurrency | `1gb` + `100mb` | two parallel clients | both checksums ok; peak RSS < 2× S1 |
| S7 | curl vs httpx | `100mb` | `--mode curl` | durations comparable; curl timing breakdown captured |

### Cloud run plan (keep egress small)
| Step | Runs | Variant | Scenario | Facade egress |
|---|---|---|---|---|
| Wiring check | 1–2 | `10mb` | S0 | ~20 MB |
| Iterate until clean | up to ~5 | `100mb` | S1 (+ S7 once) | ~0.5 GB |
| Recorded runs | 2–3 | `1gb` | S1 | ~3 GB |
| Optional | 1 | `100mb` | S4 | ~0.04 GB |
| **Total** | | | | **≈ 3.5–4 GB** |

S2, S3, S5 and S6 stay local unless you specifically want a cloud data point. Local runs with
`cpus: 0.1` already answer the memory/backpressure questions; the cloud runs add real WAN latency,
TLS, the redirect hop, and platform ingress behavior. With the static partner there are no
partner-side logs in the cloud, so the cloud S4 is judged on facade logs only (upstream socket
closed within 2 s of the client abort).

## 8. Deployment — three networks, $0 by default

Free tiers changed a lot in 2026; numbers below were checked late Sept 2026. **Verify before deploying.**

**Budget rules (owner's constraints):** $0 is the target. A card on file is acceptable only where
the provider does **not** place a fixed pre-authorization hold or require prepaid credit. Hard
ceiling for the whole POC: **$20**. Excluded for that reason: Koyeb (card with a $29 hold, signup
defaults to a $29/month plan) and Fly.io (no free tier).

| Role | Host | Why | Limits that matter |
|---|---|---|---|
| Partner (A) | **GitHub Releases** on the POC repo: the 4 CSVs + `manifest.json` as assets of a release tagged `test-files-v1` | No card, no compute to run. GitHub states each asset must be under 2 GiB and there is no limit on total release size or bandwidth. Downloads come from GitHub's CDN, a different network from both Render and the Actions runners. Supports `Range`. | Asset URLs `302` to a signed CDN URL (facade must follow redirects). No partner-side logs or throttling in the cloud; those are tested locally. Repo must be public for anonymous downloads. |
| Facade (B) | **Render free web service** | No card. 512 MB / 0.1 CPU mimics a small PCF container. HTTPS built in. | Hobby workspace bandwidth is **5 GB/month** outbound; the §7 plan uses ~3.5–4 GB. Spins down after 15 min idle, ~1 min to wake (`--warmup`). |
| MFT client (C) | **GitHub Actions** (`ubuntu-latest`), `workflow_dispatch` | Runs on Azure, a separate network. Inbound is free. ~14 GB runner disk fits a 1 GB write. | Public repo = free minutes. |

**Paid upgrades, only if needed (all within the $20 ceiling)**
- **More facade runs than 5 GB allows:** add a card to the Render workspace instead of suspending
  at the cap. Extra outbound is billed per GB (about $0.15/GB at time of writing), so each extra
  1 GB run costs well under $1. No hold, no plan change. Set a reminder to remove the card after.
- **Partner-side logs in the cloud** (e.g. to prove backpressure or abort teardown reached the
  partner across a real WAN): run `partner-file-api` on **Railway Hobby** ($5/month subscription,
  billed in arrears; no hold). Ephemeral disk is only 1 GB, so **bake the generated files into the
  Docker image** (image limit 4 GB; total files ≈ 1.6 GiB) by running `npm run generate` in the
  Dockerfile build stage. Egress is about $0.05/GB, so the whole run plan adds cents. Cancel after
  the POC. Switch the facade to `PARTNER_MODE=api`.
- **Facade on Google Cloud Run** (to compare a serverless runtime): card on file, billed per use;
  free egress is only ~1 GiB/month in North America, so each 1 GB run is roughly $0.12.
- Not recommended: Oracle Always Free (card verification at signup, Arm capacity often
  unavailable, allowance halved in June 2026). Avoid Vercel/Netlify functions (response limits),
  Cloudflare Workers for the facade (no process-level CPU/mem), Hugging Face Docker Spaces (paid).

### Bandwidth budget (put this in README)
Each run's egress = variant size from partner + the same from facade. MFT ingress is free.
- Partner on GitHub Releases: no bandwidth limit.
- Facade on Render: the §7 plan totals ≈ 3.5–4 GB of the 5 GB monthly cap. A 4th 1 GB run in the
  same month exceeds it — either wait for the next month or use the paid Render upgrade above.
- The MFT workflow and CLI default to `100mb`; `1gb` must be chosen explicitly.
- Have the README include a running tally table (date, variant, facade egress) so the owner can
  see remaining headroom before triggering a run.

### Static partner (`.github/workflows/publish-test-files.yml`, `deploy/github-release/README.md`)

  all 4 CSVs + `manifest.json`. Uses the default `GITHUB_TOKEN` with `contents: write`.
- This runs once. Generation happens on the runner, never on any request path.
- `manifest.json` format:
  ```json
  {
    "purpose": "settlement",
    "latest": {
      "10mb":  { "id": "file_settle_10mb",  "size": 10485760,   "sha256": "…", "url": "https://github.com/<owner>/<repo>/releases/download/test-files-v1/file_settle_10mb.csv" },
      "100mb": { "id": "file_settle_100mb", "size": 104857600,  "sha256": "…", "url": "…" },
      "500mb": { "id": "file_settle_500mb", "size": 524288000,  "sha256": "…", "url": "…" },
      "1gb":   { "id": "file_settle_1gb",   "size": 1073741824, "sha256": "…", "url": "…" }
    }
  }
  ```
  `PARTNER_MANIFEST_URL` = the release-download URL of `manifest.json`.
- S0 must confirm: redirect followed, `Range` honored after the redirect (`206`), `Content-Length`

### Render setup (`deploy/render/render.yaml`)
- Blueprint for one free web service from `facade-api/Dockerfile` (`node:22-slim`,
  `NODE_ENV=production`, non-root user). Health check: `/healthz`.
- Env: `PARTNER_MODE=static`, `PARTNER_MANIFEST_URL`, `FACADE_TOKEN` (secret, `sync: false`),
  `METRICS_INTERVAL_MS=1000`, `BUFFER_MODE_MAX_BYTES`. (`PARTNER_BASE_URL`/`PARTNER_TOKEN` only if
  using the Railway upgrade.)
- Note in README: confirm Render's request timeout covers a 1 GB transfer and that its ingress does

### GitHub Actions (`.github/workflows/mft-run.yml`)
- `workflow_dispatch` inputs: `scenario`, `variant` (choice: `10mb`, `100mb`, `500mb`, `1gb`;
  default `100mb`), `mode`, `read_rate_mbps`, `abort_after_mb`.
- Secrets: `FACADE_URL`, `FACADE_TOKEN`. (Expected sha256 comes from `checksums.json` in the repo
  or the public `manifest.json`; `PARTNER_URL`/`PARTNER_TOKEN` only with the Railway upgrade.)
- Steps: checkout → setup-python 3.12 → `pip install -e mft-client` → `python -m mft run ...` →
  upload `results/` as an artifact → append the Markdown report to `$GITHUB_STEP_SUMMARY`.

## 9. Local mode (do this first)

`docker-compose.yml` runs all three with limits mirroring the free tiers:
- facade: `mem_limit: 512m`, `cpus: 0.1`
- partner: `mem_limit: 1g`
- optional `netem` sidecar or `tc qdisc add dev eth0 root netem delay 40ms rate 200mbit` on the
  partner container to fake WAN latency.
Local results are the control group for interpreting the cloud numbers.

## 10. Conventions
- Node: ESM, Node 22, no TypeScript build step required (JSDoc types ok). Lint with `eslint` default.
- Python: 3.12, `ruff`, `httpx`, `python-ulid`, `rich` for console output. Tests with `pytest`.
- Logs: JSON lines only, one object per line, always include `runId`.
- Config only via env vars; document every var in README with default.
- Never log tokens. Never commit generated `.csv` test files or `results/`.

## 11. Build order and acceptance checks

1. **Partner API** + generator. Check: `npm run generate` produces all 4 files at exact sizes; a
   second run skips them (idempotent); sha256 values match `checksums.json`; server request path
   never hashes or generates; `curl -r 0-99` returns 100 bytes with `206`; gzip is never applied
   even with `Accept-Encoding: gzip`.
2. **Facade stream mode** + metrics sampler. Check locally with `cpus: 0.1`: `10mb` smoke first,
   then `100mb`, then one `1gb`; peak RSS delta < 64 MiB; samples present for all phases.
3. **MFT client** httpx mode, then curl mode, report generator. Check: report renders; checksum ok.
4. **Scenarios S2–S7** locally. Each must produce a result file and pass its criteria.
5. **Deploy**: run `publish-test-files.yml` once → facade to Render with `PARTNER_MODE=static` →
   MFT via `mft-run.yml`. Follow the cloud run plan in §7: `10mb` wiring check → `100mb` until
   clean → 2–3 × `1gb` recorded runs. Stop and tell the owner before any step that would exceed
   Render's 5 GB or incur a charge.
6. **README** with: architecture diagram, env vars, deploy steps per host, bandwidth budget, and a
   results table template (run × variant × duration × peak RSS × CPU ms/GB × TTFB).

## 12. Optional extension (AI/LLM learning track)
After phase 6, add `mft/analyze.py`: send the merged run JSON (samples downsampled to ≤200 points)
to an LLM API (e.g. Anthropic Messages API with a JSON-schema tool for structured output) and ask
it to flag anomalies — memory growth slope, throttling-bound vs network-bound throughput, TTFB gap
suggesting proxy buffering. Write its findings into the Markdown report under "Automated analysis".
Keep it behind `--analyze` and an `ANTHROPIC_API_KEY` secret; the POC must work without it.
